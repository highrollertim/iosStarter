1What RepoScout Is

RepoScout is a small, complete iOS app: you search GitHub's public repository API, browse results, open a detail screen, and save favorites that persist locally. That functionality is deliberately modest — the app exists to be read, not shipped. Every file demonstrates how a professional iOS team would build this in 2026, and the doc comments explain the why behind each pattern.

How to read this guide: Section 4 walks one keystroke through the entire system — read it first; every later section deepens one hop of that journey. Sections 5–11 are the design decisions worth stealing. Section 12 is the concurrency chapter — it explains SE-0461, the change to what async means that most material written before 2025 silently gets wrong. Sections 14–17 cover the testing and shipping practices that separate a demo from a product.

Third edition. This codebase has now been through two rounds of independent, adversarial audit (SwiftUI idiom currency, hostile concurrency review with compiler probes, and professional-completeness review including a native-quality pass over the German localization), each followed by a full remediation. Several sections teach lessons that exist because an audit caught an earlier version getting them wrong — those are told as "here is the mistake and why", because that is the most durable form of the lesson. This document's HTML source is committed at docs/guide/, so it can be corrected and re-rendered by anyone.
Naming note. The Xcode project, targets, and schemes are still named testExample; the product is RepoScout via display name, a real icon, and the bundle ID work.timmaher.RepoScout. Renaming a pbxproj is high-churn, low-value work; product identity and project naming are independent, and leaving them different demonstrates that.

2Running the App and the Tests

Open testExample/testExample.xcodeproj in Xcode 26.2 or later and run the testExample scheme. The scheme is shared (committed under xcshareddata/xcschemes/), so these commands work on a fresh clone. All commands run from the testExample/ directory that contains the .xcodeproj:

cd testExample

# Unit tests (Swift Testing) — runs under the test plan, in English AND German
xcodebuild test -project testExample.xcodeproj -scheme testExample \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -only-testing:testExampleTests

# UI tests (XCUITest, BDD-style) — boots a simulator, slower
xcodebuild test -project testExample.xcodeproj -scheme testExample \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -only-testing:testExampleUITests

# Everything, both languages (~11 minutes)
xcodebuild test -project testExample.xcodeproj -scheme testExample \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

Substitute any installed simulator for the name= value. The scheme runs a committed test plan (testExample.xctestplan) with two configurations — English and German — so every test invocation exercises both localizations, with code coverage collected for the app target (about 90% across the full suite). The UI tests never touch the network: they launch the app with debug-only arguments (Section 11) that swap in a deterministic mock client and an in-memory database.

4The Life of a Search — an End-to-End Trace

Suppose the user types "swift" into the search field.

keystroke → .searchable binding → SearchViewModel.searchText (didSet)
  → querySubject.send() → Combine: debounce(300ms, main) → filter(trimmed ≠ lastDispatchedQuery)
  → sink → dispatch(query) (records key, cancels old task, starts new — the ONLY entry point)
  → state = .loading (first load) or .loaded(stale, isRefreshing: true) (refinement)
  → await client.searchRepositories() (@concurrent — leaves the main actor here)
  → URLRequest (Accept, User-Agent, 15s timeout, + encoded as %2B) → JSON → RepoDTO → Repo
  → state = .loaded([Repo], isRefreshing: false) → @Observable invalidates SearchView
  → switch state → List of RepoRowView (exhaustive — compiler-checked)
  1. The binding. .searchable with autocapitalization and autocorrection disabled (repository names are identifiers — iOS would "fix" vapor into vapour), and the iOS 26 .searchToolbarBehavior(.minimize). Return calls submitImmediately(), skipping the debounce the user has already outrun.
  2. Into the stream. searchText's didSet feeds a Combine PassthroughSubject — the moment a value becomes an event in a stream.
  3. The pipeline. debounce waits out the typing; then a filter compares the trimmed candidate against lastDispatchedQuery. Why a filter and not removeDuplicates() is Section 8's lesson.
  4. One funnel. The sink calls dispatch(_:) — the only way any code starts a search. It records the dedup key, cancels the previous task, starts and stores the new one. Return, Retry, and pull-to-refresh all go through the same door, which is what makes "the newest search wins" a guarantee instead of a habit.
  5. State respects the screen. A first load shows a spinner; a refinement keeps the stale results visible with a small indicator (isRefreshing); a refinement that fails keeps them too, with an error bar (Section 7).
  6. The network, off the main actor — explicitly. The production client is @concurrent; under SE-0461 that attribute, not the async keyword, is what moves the request and decode off the caller's executor (Section 12).
  7. JSON becomes domain via Repo.init(dto:) — the single seam where GitHub's vocabulary ends.
  8. The UI is a function of state. SearchView.content switches over LoadState with no default.

5The Model Layer: Three Shapes for One Repository

TypeShape belongs toChanges when…
RepoDTOGitHub's APIGitHub changes their JSON
RepoThis app's domainThe app's needs change
FavoriteRepoThe on-disk schemaA migration is written

Three types that rhyme, on three different clocks, connected by exactly one conversion each (Repo.init(dto:), FavoriteRepo.init(repo:), FavoriteRepo.asRepo). Repo is a nonisolated struct: Identifiable for List, Hashable for value navigation, Sendable so it can legally cross the executor boundary the @concurrent client creates. The DTOs use explicit CodingKeys over a global snake_case strategy — boilerplate traded for greppability.

Validation lives at the seam: Repo.webURL returns the repository URL only when its scheme is http(s) — compared case-insensitively, since URL schemes are case-insensitive per RFC 3986. The risk being guarded is a server-controlled custom scheme deep-linking into another installed app; the detail screen renders its GitHub link only through this property.

6The Service Layer: a Protocol, Typed Errors, and Honest HTTP

nonisolated protocol GitHubClient: Sendable {
    func searchRepositories(matching query: String) async throws -> [Repo]
}

One method, async, returning domain models. Seven conformances exist across the project: the production client, the DEBUG mock actor, and five actor-based test doubles (Section 14) — and nothing downstream can tell them apart. That substitutability is the testing strategy.

The live client

LiveGitHubClient builds a real URLRequest: 15-second timeout, Accept: application/vnd.github+json, and a User-Agent (which GitHub requires). Two details the audits sharpened:

  • + is percent-encoded by hand. URLComponents legally leaves + raw in a query value, but GitHub form-decodes it as a space — so c++ silently searched for c. The client rewrites + to %2B after building the components, and a test pins it.
  • Status codes are read the way GitHub actually sends them (excerpt; comments abridged from the source): 
    case 200..<300: break                       // any 2xx is success
case 400, 422: throw .invalidQuery          // GitHub's answer to a malformed/empty query
case 403:                                   // overloaded: rate limit AND plain forbidden —
    // claim "give it a minute" only when x-ratelimit-remaining / Retry-After say so
case 429: throw .rateLimited
default: throw .server(statusCode:)

Cancellation is normalized — URLSession reports a cancelled task as URLError(.cancelled), which the client surfaces as CancellationError so callers handle one shape. What the caller does with it matters more, and is Section 8's story: the view model's catch asks the cancellation flag, never the error type, because a CancellationError can arrive on a task that was never cancelled (session teardown), and trusting the type once produced an unrecoverable forever-spinner.

The mock client

MockGitHubClient is a DEBUG-only actor in the app target (previews and UI tests run the real binary). Scenarios, chosen by environment variable: success, searchError, emptyResults, and searchErrorOnce — which fails the first completed call per distinct query, making the Retry-recovers UI test immune to typing speed (a slow keystroke burning the failure on "s" no longer steals it from "swift"). Its 300ms delay sits before the scenario switch, so a cancelled mock call throws like the real client would.

7LoadState: Stale-While-Revalidate and Failure That Keeps Your Work

nonisolated enum LoadState<Value: Sendable & Equatable>: Equatable, Sendable {
    case idle
    case loading
    case loaded(Value, isRefreshing: Bool)
    case failed(message: String, stale: Value?)
}

The core argument is the classic one: a bag of isLoading/items/error properties has eight combinations, most nonsense; a closed enum has exactly one state and the compiler guarantees every case a screen. What two audit rounds added is that the naive four-case version of this enum fails its own sales pitch twice:

  • isRefreshing — without it, refining a query must either blank the results to a spinner (the screen flickers on every debounced keystroke — the v1 behavior) or lie about the request being done. "Results on screen while a refinement is in flight" is a legal, necessary state. The Bool lives inside loaded so "refreshing with nothing to refresh" stays unrepresentable.
  • stale on failed — a refinement failure is not a reason to throw away the last thing that worked. With results showing, failure renders as a compact error bar over the still-readable results; a first-load failure carries nil and selects the full-screen error. Optional rather than a fifth case, so the view still has one failure branch.

Two companion details: the empty-results title comes from lastCompletedQuery — the query that produced the empty set — never from the live field text, which is still ahead of the debounce and may describe a search nobody has run; and the empty branch renders isRefreshing as a small overlay spinner instead of discarding it with a wildcard, so refining from an empty set visibly does something.

8SearchViewModel: One Funnel, One Dedup Key, One Scoped Ticker

dispatch(_:) — the only door

@discardableResult
func dispatch(_ query: String) -> Task<Void, Never> {
    lastDispatchedQuery = query.trimmingCharacters(in: .whitespacesAndNewlines)
    searchTask?.cancel()
    let task = Task { await self.search(matching: query) }
    searchTask = task
    return task
}

search(matching:) is private; the debounce sink, submitImmediately(), retry(), and pull-to-refresh all go through dispatch(_:). This came out of an audit finding, and the reasoning is worth keeping: the design's safety rests on two invariants — every in-flight search is searchTask (so cancelling it is a complete statement), and the dedup key always describes the search actually running. When search was internal and did its own bookkeeping-free work, those held only by convention; the first future caller (pull-to-refresh was the obvious one) would have broken them into a genuine stale-clobbers-fresh bug. Funnelling makes the invariants structural, and returning the task lets tests and .refreshable await completion without touching internals.

Why filter, not removeDuplicates()

removeDuplicates() dedups on the input, which is only sound when the operation is deterministic — and a network search is not. With it, a failed search became unrepeatable by typing: the operator remembered the failed query forever. The replacement dedups against lastDispatchedQuery, which the outcome controls: recorded on dispatch (so a Return-then-debounce pair can't double-fire), cleared on failure (so retyping retries), kept on success (so identical re-submissions stay suppressed), and trimmed on both sides (so "swift " isn't a "different" query worth a second request).

One catch, asking the flag

The failure path has a single catch, and it checks Task.isCancelled — never error is CancellationError. The distinction is load-bearing: a CancellationError can arrive on an uncancelled task (the client normalizes every URLError(.cancelled), which URLSession also produces for session teardown). An earlier version trusted the type and could exit leaving .loading on screen forever — with the dedup key still pinned, so retyping was filtered, and no Retry button, because Retry renders on .failed. Asking the flag covers both worlds: a genuinely superseded search returns silently; anything else becomes a .failed the user can act on. The post-await guard !Task.isCancelled before the success writes is airtight for a stated reason — cancellation can only originate on the main actor, and there is no suspension point between the check and the writes — and the comment says exactly that, because the pattern is not airtight in a class where cancellation can arrive from a background context.

The ticker

Combine's second appearance: Timer.publish, started/stopped by the results list's appear/disappear (an init-started timer on an app-lifetime object would fire forever on every tab), seeded on start (Timer.publish's first emission is a second away; without the seed, returning to the tab showed a stale timestamp for a beat), and read only by a leaf view (Section 9). The max(0,…) clamp's comment is now honest: it does fire — the first body evaluation runs before .onAppear seeds the clock — and in steady state Int truncation is what absorbs sub-second lag, not the seed.

Type-checks vs. is-safe. The Combine sink closures are marked @MainActor, and the comments name scheduler: DispatchQueue.main / on: .main as load-bearing. Precision matters here: default MainActor isolation is why the closures type-check touching state; the scheduler arguments are why that's true; and the @MainActor annotations insert a dynamic check — nothing is verified at compile time, and that is the point. Swap the scheduler for a background queue and the code compiles clean, then traps loudly at runtime instead of quietly corrupting main-actor state. An audit verified the trap empirically.

9The Views: Where Logic Was Deliberately Left Out

SearchView

A pure function of viewModel.state:

StateUI
.idleContentUnavailableView invitation
.loadingFull-screen spinner — first loads only
.loaded, emptySystem no-results view titled with lastCompletedQuery; overlay spinner while refreshing
.loaded(repos, isRefreshing)The List + footer bar; .refreshable pull-to-refresh (safe because it goes through dispatch)
.failed, stale keptThe stale List with a compact ErrorBanner (message + Retry) in a bottom bar
.failed, nothing to keepFull-screen error with a prominent Retry

The footer and error bar use safeAreaBar — the iOS 26 API that supplies the system bar background and scroll-edge treatment — rather than safeAreaInset with a hand-painted .background(.bar), which on iOS 26 rendered a flat slab above the floating tab bar. Both error presentations carry the same two accessibility identifiers (search.errorView on the message, search.retryButton on the button); only one renders at a time.

A real-world scar, kept on purpose. The error identifier lives on the description text, never the container: ContentUnavailableView re-parents a container-level identifier onto its merged children, which clobbered the Retry button's identifier at runtime. The interim workaround — matching the literal English "Something went wrong" — then broke the moment the app grew German. Identifier on the one true leaf: correct and locale-independent.

LastRefreshedFooter — invalidation confined to a leaf

@Observable attributes property reads to whichever body performs them. The footer text reads now, which the ticker rewrites every second — inlined into SearchView (even inside the bar's builder closure) that read would belong to SearchView.body, re-evaluating the whole screen once a second. As its own small struct, the per-second dependency belongs to a view whose body is a spinner and a Text. The comment is precise about two things the first edition fudged: re-evaluation is not re-rendering (structural diffing elides unchanged rows — the cost is real but smaller than "the whole screen re-renders"), and the insulation is one-directional (the leaf still re-runs when the parent invalidates; that direction is harmless). The spinner is no longer gated on the timestamp's existence — progress and "a previous request finished" are unrelated facts — and the whole bar is .accessibilityHidden(true): a label that changes every second is hostile to VoiceOver, and this is ambient status, not content.

RepoRowView

  • Star counts render via .formatted() (locale grouping) — the v1 raw interpolation both skipped grouping and minted a meaningless bare %lld key into the catalog.
  • ViewThatFits reflows the stats row vertically at accessibility text sizes; the summary's line limit lifts when dynamicTypeSize.isAccessibilitySize.
  • De-emphasized text uses a semantic asset-catalog color with Any/Dark and Increase Contrast variants — replacing a fixed opacity(0.65) that passed the contrast audit but opted out of Increase Contrast and was only valid against the backgrounds it was measured on. (Stock .secondary at caption sizes measures ~3.9:1, below WCAG AA's 4.5:1 — the automated audit caught it.)
  • One VoiceOver element per row (children: .ignore — the label fully replaces the fragments), speaking whole localized sentences with correctly inflected star counts via catalog plural substitutions (Section 16).

RepoDetailView

No view model — no async orchestration to justify one. Live favorite state via a parameterized @Query built in init; writes through FavoritesStore. The toolbar button carries a stable label ("Favorite") with state in the .isSelected trait — the earlier flipping label plus trait read as the contradiction "Remove from Favorites, selected". The star swap animates via .animation(value: isFavorite) bound to the observed value (a withAnimation around the write animated nothing: the value changes later, when SwiftData's notification lands), and the haptic is driven by a toggle counter incremented in the action — not by the observed value, which fired a success buzz for merely navigating to a favorited repo, and for unfavoriting. The GitHub link renders only through Repo.webURL.

FavoritesView

Live @Query reads; the empty state is a non-hit-testable .overlay so the List keeps its identity and the last row's delete animates; EditButton appears only when there is something to edit; multi-row deletes go through the store's batch API — one context.save(), one change notification, one list rebuild.

RootView and previews

The search tab declares role: .search, with a comment that now says precisely what that buys and what it doesn't — the iOS 26 minimize-into-search behavior is the separate, explicit .searchToolbarBehavior(.minimize) opt-in, and the tab bar minimizes on scroll via .tabBarMinimizeBehavior(.onScrollDown). Both tabs carry accessibility identifiers via TabContent.accessibilityIdentifier — an API two earlier comments confidently claimed didn't exist (it has since iOS 18; the audit that caught this is why the tab query in UI tests is now locale-independent). Previews are seeded directly into every interesting state through a DEBUG-only seam (a preview renders once — it cannot wait out an async search, which is why the old "Error" preview silently showed the idle prompt forever), and the SwiftData container arrives via a PreviewModifier trait (traits: .sampleData), the iOS 18+ replacement for a global container constant.

10Persistence: SwiftData, @Query, and the Store Split

Reads via @Query in views — live, animated, no refresh bugs. Writes via FavoritesStore — dedup, save timing, and batching in one tested place. Sharpened details:

  • .unique is a safety net, not the mechanism. The dedup the app relies on is the fetch-then-branch in existingFavorite(for:). Remove the attribute and every test of the app's behavior still passes — one test exists precisely to pin the constraint itself (a direct duplicate insert collapses to one row).
  • isFavorite throws — its earlier try? conflated "the fetch failed" with "not favorited".
  • remove(_ favorites:) deletes N rows under a single save.

Unit tests run against a fresh in-memory ModelContainer per test; UI tests get the same hermeticity via a launch argument.

11The Composition Root: Dependency Injection Without Magic

AppDependencies decides every concrete implementation once, at launch. Both test hooks (-UITestMockNetwork, -UITestInMemoryStore) are #if DEBUG-gated — an audit caught the in-memory flag, a data-loss switch, being honored in Release. And the container build has no fatalError: the most common real-world container failure is a schema-migration mismatch after an app update, where crash-on-launch is an inescapable crash loop — the root logs the failure and falls back to an in-memory store, degraded but alive. Constructor injection for the view model; .modelContainer for SwiftData; the release binary contains none of the test machinery.

12The Concurrency Model: Swift 6, SE-0461, and What "async" Actually Means Now

The project compiles in Swift 6 language mode with SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor and SWIFT_APPROACHABLE_CONCURRENCY = YES — Xcode 26's defaults. The second setting enables SE-0461:

The rule that changed. A plain nonisolated async function no longer hops to a background executor — it runs on its caller's executor. If a MainActor view model awaits your nonisolated async networking function, its body — including your JSON decoding — executes on the main actor. It compiles, passes tests, and drops frames. The first edition of this codebase had exactly that bug, wearing the pre-2025 folklore ("decoded on a background URLSession task") as a doc comment. The fix is one attribute: @concurrent, which opts the function back out to the global concurrent executor. Both facts — the silent main-actor execution without the attribute, and the genuine hop with it — were verified with compiler probes during the audits, including through an any GitHubClient existential.

Where the annotations live: UI-facing code needs none (MainActor by default — which is also why FavoritesStore's fetch-then-branch has no race: two rapid taps are two serialized main-actor turns). nonisolated marks the crossing types — models, DTOs, the client protocol — and, less obviously, the shared Logger constants: a static let in an extension picks up the module's default isolation, and an accidentally-MainActor logger is unusable from exactly the @concurrent context where network failures live. Actors hold genuinely shared mutable state: the mock client and the test doubles.

13Combine's Role in 2026 — the Honest Boundary

Combine appears exactly twice — the debounced search pipeline and the scoped ticker — both genuine streams of events over time. Every one-shot request/response is async/await; LiveGitHubClient contains no Combine and says so. The boundary rule: if a value arrives once, await it; if values keep arriving, model them as a stream.

Two honest footnotes. First, operators encode assumptions: removeDuplicates() looked like exactly the right operator for the pipeline and was quietly wrong for a non-deterministic operation — the lesson is to check the assumption, not just reach for the obvious operator. Second, AsyncSequence/AsyncStream (plus swift-async-algorithms' debounce) are the concurrency-native alternative a 2026 team would also evaluate; this app teaches Combine deliberately — it ships in the OS, the operators needed are built in, and it remains what this app's readers will inherit in existing codebases. A curriculum choice, stated as one.

14Unit Testing with Swift Testing

Swift Testing throughout — @Suite, @Test, #expect/#require, parameterized cases — with @MainActor annotations where suites touch main-actor types. The supporting cast in TestSupport.swift is the real teaching content, and its roster is worth stating precisely:

  • SpyGitHubClient — records queries, returns a canned result.
  • ScriptedGitHubClient — a per-call result script; the mechanism behind the Retry-recovers test.
  • GatedGitHubClient / KeyedGatedGitHubClient — suspend requests on continuations until the test says open(), globally or per-query; both are cancellation-safe via withTaskCancellationHandler (including the pre-opened path).
  • UncancellableGatedGitHubClient — deliberately ignores cancellation. It exists because a cancellation-safe gate can never produce the scenario the post-await guard exists for: a successful response arriving on an already-cancelled task. The only double that can prove the stale result never lands is one that refuses to be cancelled. Its opposite number and it are, together, the codebase's best test-design lesson.

Infrastructure honed by the audits: poll(until:) re-checks its condition once after the final sleep and throws on timeout (the earlier version recorded an Issue and carried on — a timed-out wait could fall through into further awaits and hang the test instead of failing it); StubURLProtocol's handler sits behind a real Mutex, and withStubbedClient additionally serializes whole invocations process-wide — the Mutex removes the data race with URLSession's loader thread, the gate is what prevents two concurrent suites from answering each other's requests.

Coverage worth naming: the full HTTP mapping table (403 with and without rate-limit headers, 422, 2xx incl. 203, garbage-200, URLError(.cancelled), a clean round-trip); + encoding; the supersession invariant driven through the real dispatch path; failure-then-retype re-fires while success-then-retype doesn't; an uncancelled CancellationError lands in .failed (the forever-spinner regression test); stale results surviving a failed refinement; the empty-refinement state; ticker seeding, double-start, and stop-when-never-started; duplicate inserts; batch remove; and the localized plural labels, executed in both languages by the test plan.

15UI Testing: BDD Scenarios, Two Languages, Audited Accessibility

The shape is unchanged: Given/When/Then wrapping XCTContext.runActivity so reports read as scenarios; screen objects encapsulating queries; hermetic DEBUG-only launches. What the rounds added:

  • Scenarios that act, not just look — Retry is tapped and recovery asserted (via the per-query fail-once mock); empty results has a scenario; deletion is exercised through the visible EditButton path.
  • Keyboard-focus waits before typeText — the classic CI flake, addressed.
  • Automated accessibility audits — performAccessibilityAudit() across the screens, re-run at the largest accessibility size with suppressions removed; it caught a real WCAG contrast failure (§9).
  • Two languages, honestly. The test plan runs the suite in English and German. Queries the app controls are identifier-based and locale-independent — including the tab bar, once the false "no API for that" claim was corrected. Four test cases match strings Apple owns (the system no-results view, EditButton's title, the delete confirmation, the search field's clear button) and skip themselves outside English via an explicit XCTSkip gate — measured, visible in the test report as skips, rather than silently green. German runs: 75 test executions, 4 skips, 0 failures.
  • The launch test records an XCTApplicationLaunchMetric — a baseline-able number in the result bundle (a metric without a stored baseline records rather than asserts; the honest description) — plus the appearance-matrix screenshots.

16Localization and Accessibility

A catalog that localizes

The String Catalog carries English and a complete German localization — reviewed at native quality during the audits (the review found one grammar error and a dozen register improvements, all applied: consistent du-form, Apple-German terminology like Inhaber and Internetverbindung, Duden plurals). Every key has a translator comment; the app's name is marked shouldTranslate: false rather than "translated" to itself.

Plurals are done properly, at two levels. The footer string is spelled out ("Updated 42 seconds ago") with one/other variations in both languages — an inflecting language needs a noun to inflect. And the VoiceOver row sentences use catalog substitutions (%#@starCount@): the raw integer drives plural selection so German hears "1 Stern" / "67000 Sterne" — the technique an earlier doc claimed impossible, now demonstrated. The stated trade: the substitution's %lld drops digit grouping in the spoken count; the visible label still uses .formatted().

Accessibility as architecture

  • Rows are single VoiceOver elements speaking whole localized sentences — fragment-joining bakes in English word order and hands translators pieces they can't reorder.
  • Dynamic Type genuinely accommodated: ViewThatFits reflow, accessibility-size line-limit lifts.
  • Contrast measured, then fixed semantically — an asset color with Increase Contrast variants, not a hardcoded alpha.
  • State conveyed as state: stable "Favorite" label + .isSelected, haptics driven by the user's action.
  • Ambient noise silenced: the once-per-second footer is invisible to VoiceOver.
  • And a correction the docs now carry: accessibilityIdentifier is a test-automation hook, invisible to assistive technology — identifiers are the UI tests' contract, not an accessibility feature.

18Design Decisions, Trade-offs, and Known Edges

Decisions worth restating

  • A view model only where it earns its keep — one screen has orchestration; one screen has a view model.
  • State as a closed enum including the states everyone forgets — stale-while-revalidate and failure-that-keeps-your-work.
  • One funnel for every search — invariants made structural, not habitual.
  • Ask the flag, not the type — cancellation handling that survives errors lying about their origin.
  • The protocol seam is the testing strategy — seven conformances, no mocking framework.
  • Comments must be true under the actual build settings — both audits' deepest findings were confident prose on correct code; in a teaching codebase a wrong comment is the defect readers copy.

Known edges (deliberate, documented)

  • No pagination, auth, image loading, or iPad layout — scope, by design, with the device family matching it.
  • Four UI test cases skip outside English (Apple-owned strings with no identifier hooks); the skip is explicit and visible in reports.
  • The edit-mode delete control is queried by its system image name — List publishes it beside the row, outside any app-controlled element; measured, and documented in the screen object.
  • The spoken star count loses digit grouping to the plural substitution; the visible count keeps it.
  • CI has never executed (no remote yet); swift format's pretty-printer wrapping is advisory; the searchable field's own identifier limits are noted in the screen object and unverified against newer SDKs.
  • Negative assertions (debounce non-firing) are bounded windows — they fail open under extreme load, and say so.
